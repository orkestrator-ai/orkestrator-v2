# 11 — Implement Pi configuration management and tool-registry rebuild

Status: done — JSON CRUD, the bridge's acceptance, disabled and normalized-collision rules mirrored in the
catalog, config fingerprint in the refresh check, rebuild at the next turn, connects limited to four at a
time with a bounded close, and build digests reported for `applied` evidence. The plan's private apply

## Existing owners

- `bridges/pi-bridge/src/mcp-config.ts`: user/project resolution and protected entry.
- `mcp.ts`: bridge-owned clients, registration, inventory, cleanup and refresh key.
- `agent-session.ts`: Pi resource loader, inline extension, attach and session file.
- `http.ts`: MCP inventory and token-rotation reconciliation.
- `mcp-config.test.ts`, `mcp.test.ts`, `http.test.ts`: existing regression owners.
- `docker/entrypoint.sh`: portable Pi inputs; currently omits `agent/mcp.json`.

Pi has no vendor MCP management API to call. Configuration, clients and tool
registration are owned by this bridge. Do not advertise terminal Pi support from
a successful native-bridge implementation.

## Persistence and parsing

1. Add a source adapter for resolved `<agentDir>/mcp.json` and selected project
   `.pi/mcp.json`. Do not hardcode the agent directory independently of the Pi
   SDK/launcher resolution used by `preparePiMcp`.
2. Preserve both currently accepted source shapes: wrapped `mcpServers` map and
   bare map. Pick wrapped form for newly created files, but do not gratuitously
   rewrite existing files or lose unknown entries on edit.
3. Parse source definitions independently of runtime filtering. Keep disabled,
   invalid, unsupported and project-excluded entries visible in the editor with
   their reason. A runtime parser returning no entry is not deletion authority.
4. Validate native names before saving. Reject edits that collide after the
   existing normalization, and show pre-existing collisions as read-only conflicts
   until the user makes an explicit correction. Do not silently rename entries.
5. Implement add/update/rename/remove and persisted `disabled` behavior, confirming
   how user/project fallback should work. A disabled project entry that disappears
   from the runtime parser may expose a user entry; do not promise a global mask
   without changing and testing those semantics deliberately.
6. Offer stdio and Streamable HTTP in the first editor. Treat existing SSE-labeled
   entries as a compatibility issue; do not claim a real SSE transport from the
   current HTTP normalization. Add proper SSE only as a separately tested feature.

## Revision-aware runtime application

Add effective MCP config revision to the runtime refresh key alongside the
protected connection identity. Configuration revision covers relevant user and
project sources plus policy; changing excluded project config should not force
an unrelated session rebuild.

At a safe boundary, resolve desired definitions, construct a new generation and
rebuild both MCP connections and the inline `orkestrator-mcp` extension. Updating
the client array without updating the extension is insufficient: removed tools
would remain registered and newly added ones might never become callable.

Preserve the Pi session file and conversation state. Reuse existing detach/attach
machinery only if it has proven transcript continuity. Keep active tool calls and
approvals on their current generation until the turn finishes; queue apply during
running/cancelling/recovering states. Never use component unmount to close clients.

Choose and document failure policy: the first implementation can adopt the new
configuration with per-server failures recorded, rather than atomically requiring
every server to connect. A removed definition must stay removed even when a new
one fails. The saved config remains valid and editable; report failed health for
the individual server and preserve the mandatory internal connection.

## Resource ownership and cleanup

Retain the existing closed-generation checks around in-flight connections.
Connections that complete after retirement must immediately close and cannot
register tools on the replacement generation. Prevent concurrent user-config
refresh and Orkestrator token rotation from producing two live tool registries.

Reserve capacity for protected servers before enforcing user server limits. Bound
connections in parallel (proposed four), connect deadlines, catalog size, schema
bytes, tool names/results and close deadlines. A slow external server must not
block the bridge's event loop or suppress status for all other servers.

Track child stdio ownership precisely. Cleanup stops only children belonging to
the retired MCP generation, not the Pi session's unrelated processes. Catch
close/cancel failures; report bounded diagnostics without command/env/header
values. Release schemas and clients when retired so repeated edits do not leak.

## HTTP surface and authentication

Add private apply/capability routes through the existing bridge authorization,
bounded body readers and shared management contract. The backend remains the
configuration writer and job owner. A route can return pending-next-turn without
pretending the next Pi agent already exists.

Do not expose MCP OAuth sign-in initially: the bridge-owned MCP client currently
does not implement that flow. Header/env authentication is configurable without
claiming automatic token refresh. Pi model-provider login remains separate.
