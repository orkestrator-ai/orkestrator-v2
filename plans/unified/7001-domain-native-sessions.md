### Where Effect is used (2026-11-07)

- **Effect Schema** for all 87 definitions and the shared result shapes (`schemas.ts`), following 1001's rules. `openStruct(fields)` is `Schema.StructWithRest(Struct(fields), [Record(String, Unknown)])` typed as the plain struct: listed fields are checked and typed, every other key passes through a decode. Effect v4 has no `onExcessProperty: "preserve"`, and a domain client decodes results with `"ignore"`, so a closed `Struct` would strip the many optional fields of a projection or session record on the web. The static type is the struct's (no index signature) so the backend's model interfaces are assignable to it.
- **Deliberately not Effect:** the domain client and its web binding are promise adapters over 1009's `createDomainClient`, as in 1010 (synchronous selection, promise callers). The handlers keep their own validation helpers (`asNonBlankString`, `asNativeAgentControlUpdate`, ...) where they carry their own error text.

### Decisions (2026-11-07)

- **Argument schemas declare every key a handler reads**, because a defined command drops undeclared keys before the handler runs (pinned by `commands-registry-native-sessions-contract.test.ts`, which sends every key `asDispatchNativeAgentPromptInput` reads). A key read with `asString`/`asNonBlankString`/`asNumber`/`asRequiredBoolean` is typed (`Schema.String`, ...), which gives the same text (`Expected environmentId to be a string`); a key read leniently or checked with its own message (bounded strings, positive integers, nested records such as `update`, `action`, `resolution`, `layout`, the dispatch's `images`/`attachments`/`schema`/`command`) is `optionalKey(Unknown)`, so nothing accepted today is refused and every message is unchanged. Considered typing the nested records with Effect Schema; rejected for now: their parsers keep exact user-facing text and some (control updates) refuse unknown fields on purpose, which a tolerant schema would undo.
- **Strict handlers made tolerant:** the two subork commands (`assertOnlyKeys` on the arguments) now drop unknown keys. **Kept strict on purpose:** the nested `baseLayout`/`desiredLayout`/`selectionIntent` envelopes of `apply_pane_layout_intent` and the control update of `update_native_agent_controls`/`adopt`/`resume` (`asNativeAgentControlUpdate` refuses unknown fields): these are values whose unknown parts would change meaning if dropped (a layout field or a composer control silently not applied), not argument keys, and their tests pin the refusal.
- **Result schemas** are derived from the backend model types (`Session`, `PersistedPaneLayout`, `PersistedPromptQueue`, `PersistedComposeDraft`, `PersistedFileDraft`, `PersistedAgentHandoff`, `PersistedNativeAgentSession`, `EnsuredNativeAgentSession`, `NativeAgentSessionProjection`, `NativeAgentDispatchOutcome`, `NativeAgentSessionActionOutcome`, `AgentInteractionApplyOutcome`, `NativeAgentResumeEntry`, `NativeAgentForkOutcome`, `NativeAgentAuthStatus`, `NativeAgentToolDetails`, the goal and subork reads, `AgentInteractionObservation`, the sync capabilities, `NativeAgentDomainUpdate`/`NativeAgentLiveUpdate`/`NativeAgentProjectionUpdate`/`NativeAgentMessagePage`, `EnvironmentHydrationBatch`, `ConditionalResourceSnapshot`). No structured result is `Unknown`; `Schema.Unknown` appears only for values the model itself types as `unknown` (queued messages, draft `value`, handoff `snapshot`, pane `root`, transcript rows). Fields are optional (`Schema.optional`, which also accepts an explicit `undefined` a handler spreads) apart from discriminators (`outcome`, `status`) and fields the handler itself always writes, because the services are faked in tests with partial records and results are validated there; a present field is still type-checked. Enumerations a newer backend may extend are `Schema.String`. Progressive view updates are one open struct with `status` rather than a union of branches, so a newer status still decodes and the renderer's own `isNativeAgent*Update` guards keep deciding validity. Which fields are always present converges with the models in [7010](7010-converge-models.md).
- **`encoded: true`**: `get_native_agent_transcript_update`, `get_native_agent_live_update`, `get_native_agent_projection_update` and `get_native_agent_message_page` (the four `markSpliceableResult` handlers). They still have real result schemas, which the client decodes.
- **`access`**: `workspace` for every command (none is in `isWorkspaceExcludedCommand`, and the realm's observed list from 0006 includes `apply_pane_layout_intent`, `create_session`, `delete_compose_draft`, `get_agent_handoff_capabilities`, `get_compose_draft`, `get_pane_layout`, `get_sessions_by_environment`, `list_environment_hydration`, `list_prompt_queues`, `load_session_buffer`, `save_session_buffer`, `update_session_activity`), except `admin` for `get_agent_interaction_observations`, `reconcile_agent_interactions` and `set_agent_interaction_monitor_adoption`: machine-wide diagnostics and a machine-wide toggle that no client calls (nothing enforces `access` until 7012). The host actions (`open_in_browser`, `reveal_in_file_manager`, `open_in_editor`, `open_local_in_editor`) stay `workspace` because a leaf's workspace window calls them today; 7012 may narrow them. **`read`** equals `isNodeReadCommand(name)` (pinned by the protocol test).
- **Critical fields**, per field:
  - `requestId` on both dispatches: the idempotency key; a receiver ignoring it would run a retry twice.
  - `command` on both dispatches: a non-literal intent read as typed text would run something else.
  - `schema` on both dispatches: the caller parses structured output; ignored, the turn answers prose.
  - `images`, `attachments` on both dispatches: ignoring them sends the prompt without its files.
  - `approvalMode`, `interactionPolicy`, `executionProfileId` on the dispatches and `ensure`/`adopt`: safety options; ignored, the session runs under its defaults.
  - `expectedProviderSessionId` on `adopt_native_agent_session`: the compare-and-swap guard.
  - `messageId` on `fork_native_agent_session`: ignored, the fork copies the whole conversation.
  - `batchId` on `stop_native_agent_suborks`: ignored, every call of the session stops.
  - `expectedRevision` on `save_compose_draft`, `delete_compose_draft`, `save_file_draft`, `delete_file_draft`, `delete_pane_layout`: the compare-and-swap guard; ignored, another client's newer write is lost. (`save_pane_layout` requires it in every version.)
  - Not critical: `patchVersion`, `knownToken`/`transcriptToken`/`stateToken`, `forceSnapshot` (ignored, the answer is a fuller snapshot), `includeArchived`, `deviceCode`, `mode`/`sessionMode` (ignored, the safer plan mode), `clientTimeZone` (advisory), the conditional-read keys (older backends already ignore them and callers read both forms), `selectionIntent`, `controls`.
- **Capability commands folded into version 1.** A node that advertises `native-sessions` builds, delivers and prunes handoffs (`NATIVE_SESSIONS_HANDOFF_CAPABILITIES`) and speaks the sync protocols this build knows (`NATIVE_SESSIONS_SYNC_CAPABILITIES`: projection sync and history paging 1, progressive views 1, observation events, transcript patches, live update), so the version-1 adapter answers `handoffCapabilities()`/`syncCapabilities()` without a round trip. A later build that dropped one of them would have to bump the domain. Version 0 asks the commands on every call as before (no per-generation `capability()` cache: the web already caches per node scope with its own recheck rules, and a client bound to the module-level command-scope shim would carry the cache across suites). Both commands stay registered, as defined commands, for pre-contract renderers (new register row). `get_native_agent_sync_capabilities`'s `observation` stamp is not used by any client; it stays in the command's answer.
- **Client API**: one function per command keyed by name (`api.get_native_agent_session(args)`), built from `NATIVE_SESSIONS_COMMANDS`, plus the two capability reads. Version 1 calls `call(def, args)` (envelope, decode).
