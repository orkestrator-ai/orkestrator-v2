Findings
1. Build pipeline advancement engine is renderer-component-hosted (highest structural risk)
apps/web/src/components/build-pipeline/BuildChatTab.tsx:561-838 ("Pipeline advancement logic - watches for session idle transitions", advancePipeline at 591); same pattern in CodexBuildChatTab.tsx (~374-390 + advance effects) and OpenCodeBuildChatTab.tsx.

Recommended home: a globally mounted supervisor (the LoopedReviewSupervisor pattern already exists and is mounted at App.tsx:614) or backend-side stage advancement. Pipelines are the one long-running workflow still driven from unmount-prone components.

Frontend state ownership review
I ran four parallel review agents over the Zustand stores, hooks/contexts, and component-local state in apps/web, cross-checking each against the backend command registry, storage service, and bridge APIs. The good news first: most of the app already follows the intended architecture — prompt queues, build-pipeline snapshots, pane layout, diff stats, agent activity, and approval/question rehydration are all backend-authoritative with proper snapshot catch-up. The problems cluster into two categories: renderer-only orchestration loops (real work that stops when no window is alive) and unsaved user input held only in renderer memory.

High priority — authoritative state or work drivers that live only in the renderer
1. PR monitoring is entirely renderer-driven, and only polls the active environment.
apps/web/src/stores/prMonitorStore.ts + apps/web/src/hooks/usePrMonitorService.ts. The tick loop (usePrMonitorService.ts:376-427), the mode state machine, and the merge side effects — moving the kanban task to "review", posting the merge comment, setting prMergeCommented (:230-322) — all run in a hook mounted at the app root. Inactive environments are explicitly demoted to idle (:462-470), and the backend only exposes one-shot detect_pr commands (apps/backend/src/core/commands.ts:6507). If a PR merges while its environment is inactive or the app is closed, nothing happens until the user re-selects that exact environment — a direct violation of the "environments keep working in the background" rule. A "watch for the PR I just created" request (usePullRequest.ts:97-110) is also lost on reload because it only mutates renderer memory. Recommendation: move the polling service into apps/backend/src/core/, following the same pattern as the diff-stats migration (commit acd2a603); environmentDiffStore's snapshot-plus-incremental design is the template for the slimmed-down renderer store.

2. Build pipeline state is durable, but the engine that advances it is not.
The pipeline snapshot layer is excellent (CAS revisions, backend persistence, restart reconciliation). But phase transitions — detecting session idle, dispatching the next phase's prompt, iterating review loops — fire only from effects inside BuildChatTab.tsx:561-838 (and the Codex/OpenCode variants), kept alive by the hidden-mount workaround in App.tsx:646-669. Consequences found: if the app quits mid-phase, the agent turn finishes in the bridge but the pipeline sits at that phase until a client reopens; if the user closes the build tab, advancement silently stops with no error recorded; the duplicate-build guard for GitHub issues checks only the local store (useBuildPipeline.ts:254-264), so two clients can start builds for the same issue; and a reload during handleBuildFeature (FeaturesView.tsx:1831-1880) can leave a running pipeline with no feature linkage. Recommendation: a backend (or at least globally-mounted supervisor, like the existing LoopedReviewSupervisor at App.tsx:614) stage-advancement driver keyed off agent status, plus a backend uniqueness check on (repo, issueNumber).

3. Unsaved file-editor edits exist only in renderer memory — and are deleted on tab unmount.
apps/web/src/stores/fileDirtyStore.ts:14-16 holds dirty editor content in a plain Map with no persistence anywhere, and useFileSave.ts:88-94 removes entries on unmount. The pane layout is backend-persisted, so after a crash the file tab comes back — but its content silently reverts to disk. Recommendation: debounced draft persistence to the backend storage service keyed by (environmentId, filePath), mirroring the prompt-queue pattern.

4. Initial-prompt image attachments are lost on restart.
claudeOptionsStore.ts:7-44 — the rest of the launch intent (pendingAgentLaunch, initialPrompt, model, effort) is durably stored on the environment record, but initialPromptAttachments (base64 images from the create dialog) has no backend counterpart. After a restart mid-launch, the agent receives the prompt without the images the user attached, silently. Recommendation: store attachments on the environment record, or write them into the workspace at creation time rather than launch time.

Medium priority
5. Plan mode silently resets to bypassPermissions. claudeStore.ts:114,359-364 — per-session compose preferences are renderer-only; after a restart, a user who had plan mode on will send their next prompt with bypassPermissions without any action on their part. It's the one "preference" whose loss changes what the agent is allowed to do. Persist it in the bridge session snapshot (which already round-trips per-session metadata).

6. In-progress answers to blocking agent prompts are component-local. QuestionCard.tsx:328-340, CodexInteractionCard.tsx:68-72, ClaudePlanApprovalCard.tsx:102-105, tmux plan/elicitation cards. The prompts themselves rehydrate correctly from the bridge, but a user midway through a multi-question form or typing plan-rejection feedback loses everything on an environment switch. Store-level draft maps keyed by request ID would fix this — backend not required.

7. Initial-prompt dispatch can duplicate. CodexChatTab.tsx:194,2217-2244 (and the Claude/OpenCode equivalents): the "already dispatched" flag is component state while the launch prompt is durable, so an unmount between dispatch and confirmation re-sends under a fresh requestId that the bridge's dispatch journal can't dedupe. Relatedly, unconfirmedDispatchRef (:224-238) dies on unmount, stranding optimistic messages. Both belong in codexStore / a persisted dispatched-marker, or routed through the prompt queue, which already has backend claim semantics.

8. In-flight destructive operations have no backend status. environmentStore.deletingEnvironments (:47) and the ActionBar's singleton isDeleting/isMerging flags (ActionBar.tsx:232-236) — a restart mid-delete loses the indicator while the backend operation may still be running, and the singleton flags attribute a merge spinner to whatever environment is currently selected. A per-environment lifecycleOperation field in environments.json would cover both.

9. Two "works only while a renderer is alive" gaps worth deciding on deliberately: queued prompts drain only while a chat tab is mounted somewhere (useNativeMessageQueue — backend claim semantics exist, but nothing backend-side dispatches when a turn ends); and native-agent activity/unread status ultimately depends on a renderer holding the SSE connection (useGlobalActivityMonitor.ts:1182-1184 admits this). The bridges are the natural authority for both.

Low priority / cleanups
Compose and comment drafts (terminalSessionStore.ts:67-70, featurePlanStore.chatDrafts, GitHub/Linear comment drafts, KanbanTaskDialog.pendingImages) — unsent user text lost on restart. Low stakes individually, but it's a recurring class; a drafts bucket in backend storage would sweep them all.
loopedReviewStore localStorage layer — backend authority is correct and wired; the localStorage mirror is now redundant and serializes full diffs/file contents (size and sensitivity concern). Candidate for removal.
dismissedPromptSuggestions (claudeStore.ts:123-133) — dismissals should be a bridge-side clear so suggestions don't reappear after restart.
