# 5005 · Optional: multiplexed relay event stream

- **Report:** [§6.2 Connection budget](../../docs/reports/unified-federation.md#62-browser-and-ios), [§13.4 C](../../docs/reports/unified-federation.md#134-browser-path-to-leaves)
- **Depends on:** [0004](0004-measurement-report.md), [4002](4002-hydration-tiers-and-budgets.md)
- **Condition:** do this only if [0004](0004-measurement-report.md) or [4006](4006-multi-node-qualification.md) shows HTTP/1.1 connection pressure on the relay path after direct-first routing, WebSocket terminals and suspension. Otherwise set `dropped` with the measured reason.
- **Size:** M
- **Track:** S (scopes), backend

## Goal

One long-lived request carries the main event streams of N relayed leaves.

## Work

- [x] Backend route `/__orkestrator/nodes/events?nodes=a,b`, merging N leaf main streams.
  - Per-node cursor, echoing the client's cursor on `connected` (invariant 8).
  - Subscribe before computing replay (invariant 7).
  - Explicit byte and count bounds on every buffer (invariant 11).
  - Grant-authorised per node, refusing nodes the client holds no grant for.
  - Estimated at 250-400 LOC plus tests.
- [x] Do not extend `NodeEventRelay`: it is built for prefix leases with no terminals.
- [x] The browser node client uses the multiplexed stream when several relayed nodes are warm, and falls back to per-node streams on an older command node (404 or 405 means an older backend).
- [x] Add a register row if the client branches on the command node's version.

## Done when

- [x] Either it is implemented with tests and measured relief, or it is dropped with the measurements that justify that.

## Notes

- **Condition: met, so implemented (2026-11-07, the user's instruction).** The user asked for 5005 only if 0004's measurements show pressure. They do ([unified-federation-measurements.md](../../docs/reports/unified-federation-measurements.md), "Transport"): `nextHopProtocol` is `http/1.1` on loopback, direct and relayed; each relayed realm held 3 long-lived streams; with 2 relayed realms 50 requests waited more than 30 s with no response (13 of them the window's own: `watch_node_events` 6, `invoke_on_node` 6, `get_system_usage` 1) and a 3rd realm never rendered within 60 s (55 waiting). [2013](2013-second-scope-proof.md) measured that one relayed in-tree leaf brings the command origin to 5 long-lived requests (`/events` ×2, `/session`, `/client-metrics`, the leaf's relayed `/events`), one short of Chromium's six per origin. In-tree leaves (4001) and suspension (4002) cut a relayed leaf to one stream, but a third warm relayed leaf still needs a seventh connection.
- **API (2026-11-07).**
  - Protocol `@orkestrator/protocol/multiplexed-relay-events`: `MULTIPLEXED_RELAY_EVENTS_PATH` (`/__orkestrator/nodes/events`), `multiplexedEventsQuery(nodes)` / `parseMultiplexedEventsQuery(params)` (`nodes=a,b`, `workspace.<id>=`, `since.<id>=`), `encodeMultiplexedNodeFrame(nodeId, id, data)`, `multiplexedFrameNode(event)`, `encodeMultiplexedControlFrame` / `parseMultiplexedControlFrame` (Effect Schema, tolerant), `encodeSseFrame`, bounds `MAX_MULTIPLEXED_NODES` 8, `MAX_MULTIPLEXED_STREAMS` 32, `MAX_MULTIPLEXED_FRAME_BYTES` 8 MiB, `MAX_MULTIPLEXED_QUEUED_BYTES` 16 MiB, `MAX_MULTIPLEXED_CURSOR_LENGTH` 256, `MAX_MULTIPLEXED_WORKSPACE_ID_LENGTH` 128.
  - Backend: `NodeEventMultiplexer` (`core/nodes/node-event-multiplexer.ts`, exported from `nodes/index.ts`) with `serve(request, response, url)`, `size`, `closeAll()`; options `relayTarget`, `workspaceOpen`, `keepaliveMs` and test seams. `GatewayNodeHooks.relayWorkspaceOpen(workspaceId, nodeId)`, wired to the new `NodePortal.workspaceOpenFor(workspaceId, nodeId)`. `GatewayContext.nodeEventMultiplexer` (null without both hooks, so the route then 404s like an older command node), closed in `GatewayLifecycle.stop`; `OrkestratorGatewayOptions.nodeEventMultiplexer` (timings and bounds, tests). The route is dispatched in `GatewayAuth.handle` after authentication and the grant path check (a client grant gets 403: it is not in `GRANT_ALLOWED_PATHS`), before the per-node relay.
  - Web: `node-transport.ts` gains `openMainStream?: MainStreamOpener` (`(url, init, control) => Promise<Response>`, in place of `fetch` for the fetch-read main stream) and `MainStreamControl.reconnect()` (replace the main stream now from its cursor, no failure counted, no state change). `lib/node-scope/multiplexed-relay-stream.ts`: `createMultiplexedRelayStreams(options?) → { opener(nodeId, workspaceId), refresh(nodeId), snapshot(), dispose() }`, constants `MIN_MULTIPLEXED_NODES` 2, `REOPEN_DELAY_MS` 50, `DETACH_GRACE_MS` 5 s, `MULTIPLEXED_FALLBACK_COOLDOWN_MS` 60 s, `MAX_NODE_QUEUED_BYTES` 8 MiB, `MAX_HELD_BYTES` 256 KiB, `MAX_HELD_FRAMES` 512. `NodeClientRegistryOptions.relayStreams` (default: one per registry, disposed with it; `null` turns it off); a relayed leaf's transport gets `openMainStream`, reading the window's current workspace for the node on every open, and a reopened grant calls `refresh`.
- **Decision: wire format (2026-11-07).** Options: (a) wrap each leaf frame in JSON (`{ node, id, data }`): re-encodes and escapes every payload, larger and slower; (b) the SSE `event:` field names the node (`node:<id>`), `id:` and `data:` are the leaf's own, unchanged; control frames have no `event:` and no `id:`. Chosen (b): no re-encoding, each node's frames reach its transport exactly as the leaf sent them, so `GatewayEventStreamState` runs per node unchanged, and a control frame can never move a node's cursor. Node ids may contain `:` and `.`, so the field is a fixed prefix plus the id, never split.
- **Decision: who reconnects a leaf (2026-11-07).** Options: (a) the client reopens the whole request whenever one leaf drops; (b) the command node reopens that leaf from the last cursor it forwarded, and says `mux.node down`/`live`. Chosen (b): one leaf's outage costs the others nothing, and the cursor the command node resumes from is exactly the last frame it wrote to this client, so the leaf's own replay (or `gateway.reconcile-required`) covers the gap (invariant 4). The client fails that node's stream on `down` so its transport shows the outage and retries on its own backoff; it re-attaches to the same request without a reopen.
- **Decision: bounds and backpressure (2026-11-07).** Leaf streams are not read while the response is above its high-water mark (one shared drain wait), so a slow client slows the leaves, whose own gateways drop them under their hard limit, and the reopen from the cursor replays or reconciles. Past `MAX_MULTIPLEXED_QUEUED_BYTES` the whole response is closed rather than a frame dropped (invariant 6); the client resumes each node from its own cursor. A leaf frame over 8 MiB cannot be forwarded and would be met again on replay, so that node is reopened fresh and a `gateway.reconcile-required` node frame is sent after the new `gateway.connected`, i.e. once the new subscription is live (invariant 7). Client side: each node's stream holds at most 8 MiB unread (past it that node's stream fails and resumes from its cursor), frames between a node's streams are held up to 256 KiB / 512 frames (past it the node is sent again from its cursor), and every per-node cursor check compares the transport's own cursor (authoritative) with the last one handed to it.
- **Decision: grants (2026-11-07).** The per-node relay checks only the client's command-node credential. The multiplexed request also names, per node, the workspace the client opened for it (`open_node_workspace`; its id is a random capability handed only to that client), checked when the node's leaf stream opens and on every keepalive (25 s). A node without one is `refused` and the client reads it on its own stream until its workspace changes; a workspace closed or lapsed mid-stream is refused at the next keepalive and its leaf stream closed.
- **Decision: where the client joins (2026-11-07).** Options: (a) a shared-stream source inside `createNodeTransport`; (b) an injected opener under the transport's fetch-read main stream. Chosen (b): the transport's cursor, watchdog, backoff, credential probe and connection state run unchanged on whichever request carries the node; the transport change is the opener and `reconnect`. A node joins once at least two relayed nodes want a main stream at the same time (a warm or live scope; a suspended one has closed its streams), and the nodes on their own streams move over (`reconnect`); it stays while open (one node costs one request either way, so no switch back). Set changes cost one reopen after 50 ms, with every node's cursor; the leaves replay what the switch missed.
- **Decision: older command node and the register (2026-11-07).** A 404 or 405 means the command node predates the route: every relayed node of that page keeps its own stream for the page's life. Any other failure answer, or none (a blocked path, a connect timeout), falls back the same way for 60 s and then tries again, so a broken shared request never stalls a node. The client branches on the command node's route, so a row was added to the register in [version-compatibility.md](../../docs/architecture/version-compatibility.md#register) ("Command nodes without the multiplexed relay stream"; no counter, the older peer cannot count it). The per-node streams are not compatibility code: they stay for one relayed leaf and every direct one.
- **Not built on `NodeEventRelay`** (prefix leases for the portal, re-emitted on the command node's own stream and ring). The multiplexer keeps no ring: each leaf keeps its own, and the cursors are the leaves'.
- **Not compressed.** The response is identity: the leaf frames are already decoded by the command node's `fetch`, and the gateway's streaming gzip budget is for the main stream. A follow-up could reuse `GzipEventClientWriter`.
- **Effect: not used, deliberately.** Both halves are callback- and stream-driven plumbing under existing imperative code: the backend's leaf readers await `drain` on a Node response, and the browser half sits under a transport whose reconnect ladder is `ReconnectBackoff` (2002 kept it for the uptime-based reset). Each loop has its own single timer like every other stream owner; fibers would add a runtime boundary with nothing to compose. The control frames are decoded with Effect Schema (`decodeUnknownOption`, tolerant reader).
- **Scope.** Browser only: the desktop's node traffic goes over IPC (main reaches nodes with Node's `fetch`), and a command node behind HTTP/2 (Tailscale Serve) needs none of this but is unaffected by it. Leaf terminals stay on WebSocket (2004).
- **Outside the file set (minimal, additive).** `apps/backend/src/core/index.ts` (two lines: the `relayWorkspaceOpen` hook), `apps/backend/src/core/nodes/node-portal.ts` (`workspaceOpenFor`), `apps/backend/src/core/nodes/index.ts` (export), `packages/protocol/package.json` (export), `docs/architecture/version-compatibility.md` (register row), `docs/architecture/command-nodes.md` (one bullet).
