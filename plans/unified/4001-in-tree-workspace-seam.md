# 4001 · In-tree workspace for a leaf, behind a per-node setting

- **Report:** [§5.2 The React shape](../../docs/reports/unified-federation.md#52-the-react-shape), [§12 Phase 4](../../docs/reports/unified-federation.md#12-migration-plan)
- **Depends on:** [2013](2013-second-scope-proof.md), [3013](3013-pane-layout-store.md), [3014](3014-scoped-services-and-startup.md)
- **Blocks:** the rest of Phases 4 and 5
- **Size:** M
- **Track:** S (scopes), critical path

## Goal

With a setting on for a node, its workspace renders in the window's own React tree under a `NodeScopeProvider`, with the same code the command node uses. Every other node still uses a realm.

## Current state (verified 2026-11-07)

- The seam: `RemoteWorkspaceRegion.tsx:89-99` picks `kind === "desktop" ? <NativeRealm/> : <FrameRealm/>`, where `kind` comes from `useFederation()` (:61). `NativeRealm` is at :373, `FrameRealm` at :513 and `useRealmRequests` at :163; they are private to that file and used at :404 and :538.
- `WorkspaceRealmHost.tsx` (313 LOC) gates dialogs on readiness inside a realm.
- In `workspace-realm.ts`:
  - `isWorkspaceRealm` (:304), `postToShell` (:513) and `onShellMessage` (:525) read the URL and `window`;
  - `realmGroupingFor` (:86), `realmCoordinatorDefers` (:103) and `projectLandingTab` (:113) survive.

## Work

- [x] A setting `inTreeNodes: nodeId[]` (default empty), persisted per window and editable in Settings → Machines, with a development override. The setting is a rollback switch, not version skew (`version-compatibility.md`).
- [x] `<InTreeWorkspace nodeId>`: acquires a node scope (browser `node-clients`, desktop `orkestrator:nodes:open`), wraps `<NodeScopeProvider><NodeErrorBoundary><Workspace/></NodeErrorBoundary></NodeScopeProvider>`, and releases on unmount after the grace period ([4002](4002-hydration-tiers-and-budgets.md)). Unmount must not cancel backend work.
- [x] `RemoteWorkspaceRegion` renders `InTreeWorkspace` when `inTreeNodes.has(nodeId)`.
- [x] A realm context replaces URL and `window` reads in `isWorkspaceRealm`, `postToShell` and `onShellMessage`. An in-memory loopback implements `send`/`onMessage`, so `useRealmRequests` sequencing and `WorkspaceRealmHost` dialog gating run unchanged under the provider. [4005](4005-direct-navigation.md) then removes the loopback message by message.
- [x] `NodeErrorBoundary`: per-node error with retry. A crash in one node's tree does not take down the window shell.
- [x] The command node's own workspace renders through the same `NodeScopeProvider` path (one workspace implementation).

## Tests

## Notes

- **API (2026-11-07).**
  - Setting: `stores/inTreeNodesStore.ts`: `useInTreeNodesStore` (`nodes: string[]`, `setInTree(nodeId, on)`), persisted under `windowStorageKey("in-tree-nodes")` (per window, bounded to 64, deduplicated), `isInTreeNode(nodeId, stored, override?)`, `useInTreeNode(nodeId)`, `developmentInTreeOverride()` (`VITE_ORKESTRATOR_IN_TREE_NODES` = comma-separated ids or `*`, development builds only, adds and never removes). UI: `components/settings/machines/InTreeWorkspaceSection.tsx` ("Workspace in this window"), shown in `MachineSettingsDialog` for every machine except this one. It is a rollback switch: any node can be shown either way, so nothing depends on a version. No row in `version-compatibility.md`.
  - Scopes: `lib/federation/in-tree-scopes.ts`: `holdInTreeScope(nodeId, options?) → { scope: Promise<NodeScope>, release() }`. Browser: one lazily created `createNodeClientRegistry()` per renderer, `openLeafScope` (2004). Desktop: `createDesktopNodeClient` over `window.orkestrator.node(nodeId)`, opened as a leaf of the app window scope, awaiting `eventStreamReady` (`orkestrator:nodes:open`, as 2013's proof does). Then `startScopeServices(scope, WARM_SCOPE_SERVICES)` (3014). Holds are counted. The last release waits `IN_TREE_RELEASE_GRACE_MS` (60 s), then stops the services and disposes the scope. A scope it did not open is reused and never disposed. A scope disposed elsewhere is reopened. Also `closeInTreeScopes`, `inTreeScopeHolds`, `configureInTreeScopes` (test seam). Settings parents need no `bindSettingsParent`: an in-tree leaf is a leaf of the app window scope, so 3005's `settingsParent` gives it the window's command scope.
  - Realm protocol: `lib/federation/realm-channel.ts`: `RealmChannel` (`kind`, `isRealm`, `initialRequest`, `post`, `onMessage`), `pageRealmChannel` (the URL/`window` functions of `workspace-realm.ts`), `createRealmLoopback(initial, { schedule? }) → { realm, send, onRealmMessage, close, closed }`, `RealmChannelContext`, `useRealmChannel()`. Messages go through the same parsers as the page transports and are delivered in a later microtask, in order. A message that arrives while nobody listens is dropped. `useRealmRequests`, `RealmStatus` and `nodeName` moved unchanged from `RemoteWorkspaceRegion.tsx` to `components/federation/realm-requests.tsx`.
  - `components/federation/InTreeWorkspace.tsx`: `InTreeWorkspace({ nodeId, shown })` holds the scope, opens one loopback per document (first open, and Try again after a crash; each is `createRealmLoopback(restart())`), and subscribes the window side in a layout effect, before the realm side says `ready`. It renders `RealmChannelContext > NodeScopeProvider > NodeErrorBoundary > InTreeNodeWorkspace`. `InTreeNodeWorkspace` is `TerminalProvider`, a per-node `DockerAvailabilityProvider` (`hooks/useNodeDockerAvailability.ts`, `check_docker` on the scope every 60 s), `WorkspaceRealmHost`, `OpenFileDialog enabled={shown}`, `AgentMailPanel` (in the node's scope: 3010's leftover), and `NodeWorkspaceLayout` around `WorkspaceContent`. The container is the containing block of fixed descendants (`transform`), as a realm's own viewport is. A hidden node stays mounted, as a hidden realm does.
  - `components/federation/NodeErrorBoundary.tsx`: `NodeErrorBoundary({ nodeId, machine, onRetry?, children })`. The log is content free (`web.node-scope` `workspace.render-failed`: node id, error type, fingerprint, component chain). The event was added to `packages/protocol/src/log-vocabulary/web-sync.ts`.
  - One workspace implementation: `components/layout/WorkspaceContent.tsx` (`WorkspaceContent({ projectHomeActivation, startAllowed, dockerAvailable })`, moved out of `App.tsx` with its overlay start handlers, which now call the scope's node; `useNodeWorkspaceServices()`, `useNodeBootHydration(scope)`; `isEnvironmentContainerAvailable`, re-exported from `App`) and `components/layout/NodeWorkspaceLayout.tsx` (`NodeWorkspaceLayout`, `useWorkspaceActiveTab`, `useCentralPanelThemeVars`, `useFilesPanelPullRequestWidth`, `FILES_PANEL_MAX_SIZE`, moved out of `AppShell`). `App` renders the command node's content as `NodeScopeProvider scope={commandScope} > NodeErrorBoundary > WorkspaceContent`. A realm document's `AppShell` and `InTreeWorkspace` both draw `NodeWorkspaceLayout`. The command node's toolbar and files panel stay in the window's own layout, beside its sidebar. That frame is the window's; the content is shared.
  - `lib/backend/scope-backend.ts`: `backendForScope(scope)`: every `@/lib/backend` function for one scope. On the app's command scope it is the module itself, so mocks and spies keep working. Elsewhere it is every file's factory over `scopeBackendClient(scope)`, laid over the module and made once per scope.
  - `lib/native/browser-preview.ts` `previewNodeFor(scope)`: an attach from a tab of an in-tree node names `nodeId`, so main shows it with that node's preview runtime (2009). The window's own node and a realm document name none, as before. `useSystemUsage({ scope })` reads another node's sample on its own scope for the in-tree title-bar report.
- **Decision: the loopback is the realm side unchanged, not a parallel implementation (2026-11-07).** Options: (a) a new in-tree host that calls stores directly; (b) the existing `WorkspaceRealmHost`/`RealmTitleBarPanels`/`useRealmRequests` over an in-memory channel (report §12 Phase 4.2). Chosen: (b). The sequencing (ready, pending requests, panel seqs) and the dialog gating are the code realms already run, and 4005 removes the messages one by one. `isWorkspaceRealm`, `postToShell`, `onShellMessage` and `realmInitialRequest` stay as the page's channel. The components on the realm side read the context. **Deviation, recorded:** the imperative callers (`open-workspace.ts`, `settings-navigation.ts`, `open-bug-report.ts`, `app-shortcuts.ts`, `realm-boot-timing.ts`, `App`/`AppShell`/`GlobalSettingsHost`'s `isWorkspaceRealm()`) keep reading the page. Under an in-tree node they run in the window's document, so they take the window's direct path. That is already the "Unified" column of Appendix C.
- **Fixes the loopback needed in the realm side.** `WorkspaceRealmHost` now applies its requests to its own scope's `uiStore` (the 2 `[ui]` shim uses 3013 left; the `scoped-store-shim` baseline is now empty). It passes its node to `openDialog` (new optional `nodeId`) and `openCoordinatorWorkTarget`. It applies `visibility` to host-hidden only on the page path, because in the window's tree a hidden node must not mark the window hidden (4002 owns per-scope tiers). `LeafModeCoordinatorGate` treats an in-tree leaf as on a leaf: its gate key names the node, and it reads the command node's projects from the window's command scope in place of the portal's self summary. `OpenFileDialog` gained `enabled`, so only the shown workspace owns ⌘⇧P.
