# Step 01 — Baseline and performance contract

Status: 🟨 Implemented on branch; pending review and merge

Depends on: none

## Outcome

Create a deterministic benchmark and content-free instrumentation layer that
measures Multi Review's control-plane cost. This step changes no scheduling,
prompt, report, or review-quality behavior. It supplies the evidence and gates
used by every later step.

## Questions the baseline must answer

- How long elapses between the first and last reviewer dispatch for 1, 2, 4,
  8, and 32 reviewers?
- How many provider calls, package/artifact bytes read, workflow saves, backup
  rotations, resource announcements, and renderer refetches occur per phase?
- How much time is spent in preparation, validation, fan-out admission,
  reviewer execution, report settlement, consolidation, and cancellation?
- How many transcript reads are attempted versus actually required for progress
  detection or usage fallback?
- How large are individual reports, repeated report fields, the compactable
  portion, and the final consolidation prompt?
- Does a slow reviewer, slow provider, or retryable setup error delay unrelated
  reviewers?

## Measurement model

Add one internal measurement vocabulary shared by Multi Review and Build
Pipeline fan-out. Prefer durations, counts, byte sizes, enums, and bounded IDs.
Required dimensions are:

- workflow owner: `multi-review` or `build-pipeline`;
- phase/stage name;
- reviewer count and configured concurrency cap;
- provider platform as a fixed enum, never account/model credentials;
- outcome class: success, retryable, failed, cancelled, ambiguous, or fenced;
- cold/warm and synthetic/real-stack labels for benchmark records; and
- operation name, elapsed milliseconds, count, and byte total.

Never attach workflow IDs, session IDs, request IDs, model-generated strings,
prompts, transcripts, reports, file paths, commands, artifact names, environment
names, or error messages as metric labels. Logs may correlate through the
existing bounded opaque identifiers only where repository policy already
permits it.

## Implementation tasks

### Benchmark fixture

- [ ] Add a focused backend benchmark or deterministic performance test beside
  `apps/backend/src/core/multi-review-service.test.ts`. It must use fake
  providers, an in-memory or temporary storage root, a controllable clock, and
  generated byte buffers rather than real source or transcript content.
- [ ] Parameterize reviewer count (`1`, `2`, `4`, `8`, `32`), provider setup
  delay, send delay, status delay, report size, artifact count/size, and one
  deliberately slow reviewer.
- [ ] Include a mixed-provider case so batching or per-provider limits added
  later cannot optimize only a homogeneous panel.
- [ ] Capture an operation trace with stable event names. Assert counts and
  ordering; record wall-clock durations as benchmark output, not brittle unit
  assertions.
- [ ] Model package evidence at small, medium, and large synthetic sizes. The
  large case must remain reasonable for CI; provide an opt-in local scale case
  for hundreds of MiB without making the default suite allocate that volume.
- [ ] Add a report corpus whose contents are synthetic but whose field lengths
  and issue/gap counts match representative workflows. Report aggregate and
  repeated-field bytes separately.

### Instrumentation seams

- [ ] Define a narrow internal observer interface, for example
  `MultiReviewEfficiencyObserver`, with no-op production default and a recording
  implementation for tests. Keep it backend-local unless another package
  genuinely consumes the events.
- [ ] Instrument phase boundaries in
  `apps/backend/src/core/multi-review-service.ts` and reviewer operations in
  `apps/backend/src/core/review-fanout.ts`.
- [ ] Count integrity verification calls and bytes at
  `apps/backend/src/core/commands-review.ts`; count the package and referenced
  artifacts without exposing their paths or hashes.
- [ ] Count logical workflow saves, backup-enabled saves, resource
  announcements, and fenced write conflicts in
  `apps/backend/src/core/storage-reviews.ts` and the shared storage save seam.
- [ ] Count transcript snapshot calls and response bytes at the provider
  boundary. Distinguish supervisor progress reads from UI transcript reads.
- [ ] Count consolidation reports, source findings, serialized input bytes,
  structured-output repairs, and rejected oversize outputs.
- [ ] Ensure the observer cannot delay orchestration: calls are synchronous,
  bounded, non-throwing, and never awaited by a provider read loop.

### Baseline record

- [ ] Add `docs/improvements/multi-review/plan/baseline.md` with commit SHA,
  date, host logical cores/memory, warm/cold state, concurrent workloads, Bun
  version, fixture parameters, and results.
- [ ] Record median plus a tail percentile over enough deterministic iterations
  to distinguish noise. Do not claim production latency from fake-provider
  measurements.
- [ ] Use the measurements to fill in absolute budgets for steps 03, 05, 06,
  07, and 08. If a proposed target changes, update this index and explain why.

## Tests

- Observer failures are swallowed or isolated and cannot fail a workflow.
- Cardinality tests prove all labels come from finite enums/buckets.
- A redaction test feeds secrets and content-like strings through every observed
  operation and confirms none reach captured metric/log fields.
- The baseline trace asserts the current known shape, including repeated
  verification, eager transcript attempts, serial admission, and save/event
  counts. Later steps update those expectations as their optimization lands.
- Both the standalone service test and
  `build-pipeline-review-fanout.test.ts` emit compatible fan-out events.

Focused validation:

```bash
mise run test:logged -- --name multi-review-baseline -- \
  bun test --cwd apps/backend --preload ../../tests/setup-node.ts \
  ./src/core/multi-review-service.test.ts \
  ./src/core/build-pipeline-review-fanout.test.ts \
  --parallel=1 --only-failures
```

## Acceptance criteria

- A developer can run one documented command and compare before/after counts
  for all later optimizations.
- Measurements cover both fan-out owners and all reviewer cardinalities.
- No production behavior, prompt, persistence schema, or UI changes.
- Metrics are bounded and content-free by construction and test.
- The baseline document contains the measured gates later steps will enforce.

## Implementation record

- `apps/backend/src/core/multi-review-efficiency.ts` defines the shared
  vocabulary: closed enums for owner, operation, phase, outcome and platform;
  reviewer counts bucketed to 1/2/4/8/16/32; numeric count, bytes and elapsed
  fields only. `recordEfficiency` sanitizes every event from a whitelist, never
  throws and never awaits. The production default is a no-op.
- Instrumented seams: reviewer create/prompt/send/status/dispatch skew and task
  outcome (`review-fanout.ts`); transcript probe due/throttled, reads started,
  failed and reused (`review-fanout-transcript.ts`); evidence verification and
  permit reuse, workflow saves, fence checks, UI transcript reads, scheduler
  passes, consolidation input and launch duplicates (`multi-review-service.ts`,
  `build-pipeline-review-fanout.ts`).
- Evidence bytes are counted as the package's declared size per verification;
  artifact bytes are not yet reported by the verification command.
- Benchmark: `multi-review-efficiency.bench.test.ts` with fixtures in
  `multi-review-efficiency-fixtures.ts`. It covers 1/2/4/8/32 reviewers, a
  mixed-provider panel and a slow reviewer. It counts only through fakes and
  storage spies so the same file measured the pre-change code.
- Results and gates: [`baseline.md`](baseline.md).
- Tests: `review-fanout-support.test.ts` (sanitization, cardinality, redaction,
  isolation, bounded recorder), `multi-review-service-efficiency.test.ts`
  (no secret, ID or session content reaches recorded events), and
  `build-pipeline-review-fanout.test.ts` (the pipeline emits compatible events).
- Not done: the opt-in hundreds-of-MiB local evidence case. Verification is
  faked in the benchmark, so real hashing cost is modelled, not measured.
