# 4003 · Snapshot-first rehydration from IndexedDB

- **Report:** [§8.3 Snapshot-first rehydration](../../docs/reports/unified-federation.md#83-snapshot-first-rehydration)
- **Depends on:** [4001](4001-in-tree-workspace-seam.md)
- **Parallel with:** [4002](4002-hydration-tiers-and-budgets.md), [4004](4004-runtime-shim-guard.md), [4005](4005-direct-navigation.md)
- **Size:** M
- **Track:** S (scopes)

## Goal

Opening a node that was disposed, or opening one after an app restart, paints immediately from a bounded local snapshot, then replaces it with the authoritative read.

## Current state (verified 2026-11-07)

- **There is no IndexedDB code in the web app.** No `indexedDB`, `idb`, `idb-keyval`, `dexie`, `localforage` or `fake-indexeddb` appears anywhere. Persistence is localStorage and sessionStorage only.
- Tests run on happy-dom, which (from memory, unverified here) provides no IndexedDB, so tests need a fake.

## Work

- [x] A small IndexedDB wrapper in `apps/web/src/lib/node-scope/snapshot-store.ts`, with byte bounds per node and in total, and least-recently-used eviction. Decide between hand-written code and a tiny dependency such as `idb-keyval`; record the decision with pros and cons. A dependency needs lockfile regeneration.
- [x] A test fake: either a `fake-indexeddb` dev dependency registered for the tests that need it (not globally, per the `mock.module` rules), or an injectable backend.
- [x] Each warm leaf scope (a node shown in the window's tree) periodically writes a light snapshot: projects, environments, config, pane layout ids and last selection. The key is node-namespaced.
  - It never contains transcripts, terminal contents, file contents, prompts or credentials (invariant 12). Keep only what the sidebar summaries already expose.
- [ ] The window's own command scope writes and hydrates a snapshot too (snapshot-first paint of the command node after an app restart). Not done: see Notes, "Command scope".
- [x] On open, the scope hydrates from the snapshot and marks itself `resyncing`. The UI shows a stale marker, and mutations wait for `live`.
- [x] Clear a node's snapshot when the node is removed from the registry or on sign-out.

## Tests

- [x] Snapshot bounds and eviction; content rules (a test that tries to write a forbidden field fails); stale marker then live; mutations wait for live.

## Done when

- [x] A cold open of a previously seen node paints from the snapshot before the first authoritative read, on desktop and browser.

  - Hook points in other items' files (small, additive): `lib/federation/in-tree-scopes.ts` gained the option `prepare` (default `prepareScopeSnapshot`; `null` turns it off) and `openHydrated`, which reads the snapshot alongside the open and hydrates the scope before anything else sees it, so before 4002's lifecycle starts its services. `components/federation/InTreeWorkspace.tsx` renders `NodeSnapshotPreview` (phase `connecting`) while the scope opens and a snapshot exists, and again (phase `refreshing`) while the opened scope is `resyncing`; the real workspace mounts once it is `live`. `lib/node-scope/scope-transport.ts` `invokeInScope` waits on `scopeMutationGate` for every command that is not a read (`isNodeReadCommand`). `lib/project-environment-resource-handlers.ts` notes the environment resync's accepted read. `packages/protocol/src/log-vocabulary/web-sync.ts` gained the `web.node-snapshot` area.
- **Decision: hand-written IndexedDB code, no dependency (2026-11-07).** Options: (a) `idb-keyval` (about 600 bytes; one key-value store per database, no transactions across two stores, no index listing without reading every value); (b) `idb` (promise wrapper, ~1.2 KB, still needs the bounds code); (c) hand-written (about 120 lines). Pros of (a)/(b): less IndexedDB boilerplate, well tested. Cons: a new dependency and lockfile change for little code; (a) cannot list the eviction index without loading every body. Chosen: (c). One database `orkestrator-node-snapshots`, an index store (`meta`: node id, bytes, savedAt, usedAt) and a body store (the JSON), written in one transaction, so eviction lists only the small index. Verified in real headless Chromium (`output/agent-testing/4003/shoot.ts`, state `idb`): write (2287 bytes for a 3-project, 6-environment node), read, LRU eviction of the unread node, refusal of a forbidden field, survival across a new connection, clear and clear-all all behave as in the fake.
- **Decision: the test fake is an injectable backend (2026-11-07)**, `memorySnapshotBackend()`, passed through `createNodeSnapshotStore` or installed for the app with `configureNodeSnapshots`. No `fake-indexeddb` dependency and no `mock.module`. The bounds, eviction and content rules live above the backend, so the fake exercises all of them; the IndexedDB adapter is checked in Chromium as above. Happy-dom has no `indexedDB`, so every other suite runs with no snapshot store and is unchanged.
- **Decision: content rules are the schema's allow-list (2026-11-07).** Effect Schema, decoded with `onExcessProperty: "error"` on every write and every read: an environment's `initialPrompt`, attachments, agent settings, setup session, ports and worktree paths, a tab's prompt or file data, terminal or transcript text, and config credentials or instructions are refused, not stripped; a stored record that breaks today's rules is deleted on read. URLs with userinfo (`https://token@host`) are refused, and capture strips userinfo first. Strings are bounded to 1024 characters and every list has a maximum (invariant 11). Capture copies fields one by one, so the schema is a second line, not the only one. The config part is presentation only (enabled agents, preferred editor, terminal appearance, per-repository default and PR base branch).
- **Decision: what "live" waits for (2026-11-07).** Projects, environments and config, the three collections the hydration fills. Projects and config count when their store's `hasLoaded` turns true (any authoritative read path sets it; the hydration uses `setState` and leaves it false); environments count when the store resync's environment phase accepts a read (`noteAuthoritativeRead` in `project-environment-resource-handlers.ts`; the environment store has no loaded flag). The pane layout is not waited for: it is backend-owned and loads per environment only when that environment's workspace mounts, so it could never gate the open.
- **Decision: pane layout ids and the selection are not written into stores (2026-11-07).** Hydrating `paneLayoutStore` would make its persistence write a stale tree back to the node, and the selection is the window's (3006), not the snapshot's. Both are kept in the record and read by the preview (the selected environment, its tab count, the highlighted rows).
- **Decision, deviation from §8.3's wording: the stale paint is a read-only preview, not the full workspace (2026-11-07).** §8.3 says "the UI shows the snapshot with a stale marker until then; actions that mutate wait for `live`". The real workspace mounted on snapshot data would start terminals against a status that may be wrong (`TerminalContainer` resets the layout for a stopped container), run the once-per-environment boot restores on stale environments, and show controls whose writes would queue for up to 30 s. So the in-tree workspace shows `NodeSnapshotPreview` (the node's projects and environments, the last selection, the stale marker) until `live`, then mounts the real workspace. The scope's stores are still hydrated, so anything else reading them (and any write through the scope, which waits) behaves as §8.3 says. A side effect: the preview paints even before the scope has opened (phase `connecting`), not only after. Suggest the report say "shows the snapshot read-only with a stale marker".
- **Decision: mutations wait in `invokeInScope` (2026-11-07).** Every `backendForScope`/`scopeBackendClient`/domain-client call of a leaf passes there; a command that is not a read (`isNodeReadCommand`) waits for `live`, bounded by 30 s, then is refused with `ScopeResyncingError`; disposal refuses at once; timers and listeners are removed on every outcome (invariant 15). A scope never hydrated from a snapshot pays one `WeakMap` lookup per write and no extra await. Direct `scope.client.invokeRaw` calls (only the dev scope-proof harness) bypass it.
- **Decision: clearing (2026-11-07).** The snapshot store registers as a protected cache (`registerProtectedRichCache("node-snapshots")`): every whole-window clear (sign-out `logout`, new `credentials`, `gateway-replaced`, a `connection` or `backend-identity` change of the command scope) drops all snapshots, and a node clear (a leaf's credential reopened on a new route, or its identity changed) drops that node's. Because a browser sign-out reloads at once, `clearAllNodeSnapshots` records the request in `localStorage` first and the next start finishes it. Registry removal: the command scope's `node-snapshot` service watches the portal's node list (`portalStore`) and prunes snapshots of nodes no longer in it, once the list has loaded.
- **Command scope: deliberately not done here (2026-11-07), box left open.** The window's own node opens under a provisional id until its hello proves the real one (2001, 2011), so there is no key to read before the first read is already under way; and its boot path is `App.tsx`, a hot spot. Writing its snapshot without reading it back would be waste, so the service does not write for it. A follow-up could remember the last proven command node id per window and hydrate the command scope before `COMMAND_SCOPE_SERVICES` start.
- **Where Effect is used (2026-11-07).** Effect Schema for the record (the allow-list, bounds, the credential-URL filter, strict decoding); `Data.TaggedError` for `SnapshotContentError`, `SnapshotTooLargeError` and `ScopeResyncingError`. Deliberately not: the store's serial queue is a promise chain and the writer a timer chain, because IndexedDB is callback-based and callers are plain promises; the sync state is a plain signal (`createSignal`) that React reads directly.
- **Coordination with 4002 (concurrent).** 4002 replaced the in-tree grace timer with `WindowScope.lifecycle` in the same files. 4003's hook is independent of it: `openHydrated` wraps only the host's open promise, so a scope that pressure took back to summary is hydrated again from its snapshot when it is reopened (the §8.3 "disposed, then opened" case). 4003's InTreeWorkspace branches sit before 4002's tier branches. Commits were built from HEAD plus 4003's hunks only.
