# 2010 · Route today's invoke and listen through the command scope

- **Report:** [§6.4](../../docs/reports/unified-federation.md#64-events-must-carry-their-node), [§12 Phase 2](../../docs/reports/unified-federation.md#12-migration-plan)
- **Depends on:** [2001](2001-node-scope-core.md), [2002](2002-browser-transport-split.md), [2007](2007-desktop-node-ipc-and-events.md)

- **Size:** M
- **Track:** S (scopes)

## Goal

Every renderer call to a backend goes through a `NodeClient`, at first always the command scope's. Both host families implement `NodeClient`. Behaviour is unchanged.

## Current state (verified 2026-11-07)

- `lib/native/backend.ts` (20 lines) `invoke` checks the prefetched cache, then calls `window.orkestrator.invoke`. It has 31 production importers, 26 of them in `lib/backend/`.
- `lib/native/events.ts` (124 lines): `listen` at :53 has 34 importers; `listenOn(source, …)` is at :62.
- `authoritative-events.ts`: `listenAuthoritative` (:32) and `listenAuthoritativeWith` (:47).
- `lib/prefetched-command-responses.ts`: the `PrefetchedCommandCache` class is already per backend, with a `defaultCache` singleton at :105.
- **52 production files touch `window.orkestrator` directly**, so wrapping `invoke` and `listen` does not cover everything.

## Notes

- **API (2026-11-07).** `apps/web/src/lib/node-scope/`:
  - `browser-node-client.ts`: `createBrowserNodeClient({ nodeId, transport: NodeTransportOptions, createTransport? }) → BrowserNodeClient` (a `NodeClient` plus `baseUrl`, `url(path)`, `setCredential(token)`); `browserConnectionState(inputs)`. The client creates and owns its `createNodeTransport`, and wraps `onCredentialRejected` (it marks itself `lapsed`, then calls the owner's).
  - `desktop-node-client.ts`: `createDesktopNodeClient({ nodeId, host?, commandNodeId? }) → NodeClient` over `window.orkestrator.node(nodeId)`; `nodeRefusalCode(error)` (reads `error.code` or the `[code] ` message prefix from 2007); `desktopConnectionState(inputs)`; `NodeRefusalCode`. A client for the window's own command node (`orkestratorDesktopIdentity.backendId` by default) is `createWindowOrkestratorClient`, because main sends command-node events on the top-level channel only. `dispose()` calls `nodes.release(nodeId)`, which revokes the grant in main.
  - `listener-fanout.ts`: `createListenerFanout(attach)`, one transport subscription per event shared by every handler, with `suspend`/`resume`/`close`. Both clients use it, so `suspend()` detaches every transport subscription and `resume()` reattaches it without callers registering again.
  - `scope-transport.ts`: `invokeInScope(scope, command, args)` (the scope's prefetched cache, then `scope.client.invokeRaw`) and `clientEventSource(client)` (a `NodeClient` as `listenOn`'s source).
  - `prefetched-command-cache.ts`: `PrefetchedCommandCache` (moved unchanged from `lib/prefetched-command-responses.ts`, which re-exports it). `NodeScope.prefetched` holds one per scope, cleared on dispose.
  - `app-window-scope.ts`: `commandClient()`, `commandNodeIdFromPage()`, `resetWindowScopeForTests(commandClient?)`. With a client, it builds the next window scope around a fake command client.
  - `command-client.ts`: `commandTransportAvailable(host?)` and `commandEventStreamConnection(host?)`. The command client's `listenRaw` registers nothing on a host without `listen`, as the direct callers did.
- **Wrappers.** `lib/native/backend.ts` `invoke` is `invokeInScope(getWindowScope().commandScope(), …)`. `lib/native/events.ts` `listen` is `listenOn(clientEventSource(commandScope().client), …)`. `listenAuthoritative` goes through `listen`, so it uses the command scope with no change of its own. `primePrefetchedCommandResponses` and the other module functions act on `commandScope().prefetched`. The shared bodies live in `lib/node-scope/scope-transport.ts`, not `lib/native/*`, because `tests/setup.ts` mocks those two modules for every suite and any new export there would be missing under test.
- **Decision: the command scope's node id (replaces `provisional:command-node` where it can).** `commandNodeIdFromPage()` reads, in order, `orkestratorDesktopIdentity.backendId` (Electron main proved the window's machine before load) and `orkestratorWorkspaceTarget.nodeId` (a realm document opened for a known node, direct or relayed). It falls back to the provisional id. A hosted browser page has neither, so its command scope stays provisional until [2011](2011-scope-domain-negotiation.md) reads the command node's hello. The id is read once, when the window scope is created: a scope's id never changes, and a command-node switch reloads the page. Options considered: re-keying the scope when the hello arrives (scope ids are registry keys and store keys, so they would change under live stores); fetching the hello before mount (an extra round trip at boot, and 2011's job). `COMMAND_STORAGE_NODE` in `desktop-storage-key.ts` (3015) keeps the provisional constant. That is harmless, because the role, not the id, decides the command node's storage key.

- **Guard (`tests/source-guards/window-orkestrator-direct.ts`).** It is the first guard over production sources. `SourceGuard.productionRoots` is new: such a guard reads the non-test sources under its roots (`listProductionSources`) and never the test sources, and the test-source guards never read production files. `transportAccesses(program)` lists `window.orkestrator.{invoke,listen,eventStreamReady,eventStreamConnection,node,nodes}` reads. `tests/unit/source-guards.test.ts` asserts that no renderer file has one, so the transport category has no baseline at all. `update-baseline.ts` gains `--guard <id>` (repeatable), which rescans only those guards and keeps every other guard's committed entries byte for byte. **How the baseline was made:** `bun tests/source-guards/update-baseline.ts --guard window-orkestrator-direct`. Only this guard's 37 entries were added, and the other four guards' entries are unchanged (checked by diffing the parsed JSON). So the pre-existing findings in untouched backend, bridge, e2e and other agents' test files are not masked. The repository ratchet test still fails on those, as before, and has no finding or stale entry for this guard.
- **Where Effect is used, and where not (2026-11-07).** Not used. The connection states are pure functions of a few inputs (`browserConnectionState`, `desktopConnectionState`) recomputed on each change and published through the existing synchronous `createSignal`, which React reads with `useSyncExternalStore`. An Effect `SubscriptionRef` or a fiber-driven machine would put a runtime between a synchronous transport callback and a synchronous signal for no gain. Retries are not the client's job: the browser transport already reconnects with `ReconnectBackoff`, Electron main owns the desktop stream, and lapse/reopen is the registry's (2004). The refusal is read with a small parser rather than a `Data.TaggedError`, because it arrives as a plain bridged `Error` and nothing downstream matches on tags yet. Lifetimes stay on 2001's Effect `Scope` (the clients are disposed by the scope's `client` finalizer).
- **Behaviour changes, all small (2026-11-07).** (1) `listen` now awaits the command client's `eventStreamReady` even when the host has none (it resolves at once), so it settles one microtask later than before in that case. (2) Components that guarded with `typeof listen === "function"` now get a no-op unlisten instead of none. (3) `design-controller` always pushes its two unlisteners (no-ops without a host). (4) The command scope's id is the proven id on desktop and in realm documents (above). No visible change.
- **Desktop `suspend`.** Main owns the node's stream and its hold (the preload's `listen` takes one and nothing releases it until `nodes.release`). A suspended desktop client stops delivering and detaches its preload listeners, but the stream stays open until main's idle policy ([2006](2006-desktop-node-scopes.md)) releases the scope. If a release under live listeners lapses the client (`lapsed`), the next `eventStreamReady` reopens it.
- **Not wired yet.** Neither new client is used by the UI. The browser client is for the node-client registry ([2004](2004-browser-node-clients-registry.md)), and the desktop client is for leaf scopes once Phase 3 opens them. The command scope uses `createWindowOrkestratorClient` on both hosts.
- **Open.** None: the smoke run and its observation were done in the final live qualification pass (above). The aggregate suite (`mise run test`) is left to review preparation.
- **Observed during the smoke run (2026-11-07, Tests box 2).** Options: (a) a dev/test-only recording hook in `command-client.ts` gated on the agent-test profile flavor (as 2013's harness), which would see the client's own calls but not a module that skips it; (b) a Playwright init script that wraps `window.orkestrator.invoke`/`listen` and reads, from each call's stack, which page module called the global. Chosen (b), with no app change: in a Vite dev renderer the first page-module frame is the caller's source file, so the client (`lib/node-scope/command-client.ts`), a spec's own `page.evaluate` (no page-module frame) and a direct call from any other module are told apart, and a request-level count of `/__orkestrator/invoke` bodies (command names only) catches a command that reached the wire without passing the global at all. The wrapper patches the API object in place through an accessor on `window` (the gateway's disposer is a `WeakMap` keyed by that object, so a Proxy would break `replaceExisting`). It is opt-in, `ORKESTRATOR_AGENT_TEST_OBSERVE_INVOKES=<dir>`, installed by `browser-test.ts` on every routed context (the default context and every second context through `fetchModulesOutsideChromium`); each context writes one JSON file of names, paths and counts, never arguments. `orkestratorGateway` carries no invoke (it is `{ enabled, baseUrl }`), so there is nothing to wrap there. Commit `9d061d7aa` (`invoke-observer.ts`, `invoke-observer.test.ts` 8 cases, `browser-test.ts`, `scripts/test-all.ts`). **Run:** profile `uf-final-smoke` started as the isolated runner starts its own (4006's `start-smoke-profile.sh`), `mise run test:agent:browser` with the observer on, from a detached worktree at `9d061d7aa`: **53 passed, 1 failed, 124 skipped**, the failure the base-failing vim case "a lost terminal write stays fenced …". Observation (`output/agent-testing/uf-final/evidence/invokes/`, `invokes-summary.json`): 87 contexts over 86 tests and all 19 spec files that ran; invokes 14,535 client / 0 harness / 0 direct; listens 12,540 client / 0 / 0; wire invokes 14,160, wire-only 0 (fewer wire requests than invokes: terminal input is batched or goes over the terminal WebSocket, and the snapshot acknowledgements are answered in the page). **Positive control** in a real Chromium against the same profile (`uf-final/scripts/observer-control.ts`, `evidence/observer-control/`): a `page.evaluate` call to the global was classed `harness`, a call through `lib/native/backend.ts` `invoke` `client`, and a page module served at `/src/__observer-control-direct.js` that calls the global itself `direct` with that module named, so the zero is not vacuous. Not covered: `client-outage.spec.ts` (keeps `@playwright/test` on purpose; not in this run's selection), the desktop (the preload's `contextBridge` API is frozen; the static guard covers it), and a production bundle (no source paths in its stacks).
